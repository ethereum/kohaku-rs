# How to Contribute

Thank you for reading our contributing guidelines! We're happy to have contributions from newcomers, and I appreciate you taking the time to read our documentation.

## Submitting Changes

Please create a pull request for any changes you'd like to make. Pull requests should be made against either the `main` branch or an `experiment/*` branch. When writing pull requests, please include a clear description of your changes, the motivation behind them, and any relevant context. If your changes are related to a specific issue, please reference that issue in your pull request.

Smaller & more focused pull requests are easier to review and merge, so please stay concise. Two or three isolated small pull requests are better than one doing everything at once.

### Experiments

Experiments are entirely new changes that are not yet ready to be merged into the main branch. They live on `experiment/*` branches and are used to test new ideas that don't directly relate to existing functionality.

Experiments are explicitly not stable, and public APIs are likely to change dramatically. Consider them pre-1.0.0 under [semantic versioning](https://semver.org/). Experiments are not also not guaranteed to be maintained and may be removed at any time.

If you would like to propose an experiment, please create an issue first to discuss your idea.

### Graduating Experiments

Experiments are kept in separate branches so that main remains entirely stable and production-ready. Once an experiment is deemed stable, it can be merged into main. Before merging, the experiment will be reviewed for quality and correctness, and the public API will be stabilized. Once graduated experiments will be maintained and supported like any other code in main. 

## Testing

We use `cargo test` to run our test suite. New code should be accompanied by tests that verify its correctness. New tests for existing code are always welcome. 

Unit tests should be placed in the same file as the code they are testing, while integration tests should be placed in the crate's `tests` directory. If a test cannot be run in debug mode for any reason (e.g. generating zk proofs), it should be marked with `#[ignore]` and a comment explaining why.

We also aim to ensure that no tests require network access or secrets. This makes it easier to run tests in CI and for contributors to run tests locally. Where required, test environments should be mocked or stubbed.

See the tornadocash [integration tests](./crates/tornadocash/tests) for examples of this approach.

## Code Conventions

This repo follows standard Rust conventions, with some additional clippy lints enabled. You can see our current clippy configuration in the workspace [`Cargo.toml`](./crates/Cargo.toml). Additionally, we aim to follow [Microsoft's Pragmatic Rust Guidelines](https://microsoft.github.io/rust-guidelines/guidelines/index.html).

## LLM Usage

Code generated by LLMs will be treated like any other code contribution. You are welcome to use LLMs, but you are also fully responsible for their output. Please ensure that all code you submit meets the standards of this project and that you fully understand your changes.
